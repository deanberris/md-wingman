# Review a change to md-wingman

Use this for a local diff (`git diff main...HEAD`), a pull request number, or when running in GitHub Actions
(`.github/workflows/claude-review.yml`). The goal is a short list of real problems, most serious first, not a
restatement of the diff.

## 1. Get the change

- Local: `git fetch origin main && git diff origin/main...HEAD`, and `git log origin/main..HEAD` for the intent.
- Pull request: read its description and linked issue, then the diff. In Actions, the PR number and repository are in
  the prompt; use `gh pr diff <n>` and `gh pr view <n>`.

Read the surrounding code for anything you comment on. A finding has to hold up against the full file, not just the
hunk.

## 2. What to look for

Correctness first:

- Logic errors, off-by-one in text ranges (findings are anchored by byte offsets into the document: check UTF-8
  boundaries), races between the editor and background tasks, and a stale result applied to changed text.
- Undo/redo: each assistant change must be one undo step, and findings must live and die with their text.
- Service protocol changes kept in step on both sides (`service/src/protocol.ts` and `crates/wingman-client`), with the
  fixtures in `service/fixtures/` updated.

The repo's own rules (see AGENTS.md), each a finding when broken:

- **Never interrupt the writer.** Nothing triggered by background work may take focus, open a dialog, sheet or system
  prompt (Keychain included) or move the cursor. Results go to marks by the text, the Assistant pane or the status bar.
  Anything that may prompt happens at launch in the background or after an explicit user action.
- **Privacy in logs.** No keys or tokens in logs; document text only through `wingman_log::text` / `log.text`.
- **Claude access** goes through the Agent SDK under the user's own `claude` login (or API-key mode when chosen). Nothing
  that works around Claude Code's sign-in or rate limits.
- **Flat control flow.** Early returns, `let ... else`, let chains; no `if` pyramids. CI enforces a depth of 3, but call
  out code that is hard to follow even under it.
- **Tests.** New behaviour in the UI gets a headless UI test (see the `add-tests` skill); a bug fix gets a test that
  failed before it.
- **Docs.** README/AGENTS.md updated when build steps, settings or shortcuts change. Markdown wraps at 120 columns.
- Packaging changes go through `scripts/package.sh`, shared by `install.sh` and the release workflow.

Skip style nits the linters already catch, and personal preference.

## 3. Report

For each finding: file and line, what goes wrong and in what situation, and a suggested fix. Rank by severity. Say
plainly when you found nothing worth changing.

- Local: reply in the conversation.
- GitHub Actions: post one review on the PR with inline comments for line-specific findings (`gh pr review` or the
  GitHub MCP tools you were given), and end it with the footer below. Don't approve or request changes; leave a comment
  review. Don't push commits unless the comment that invoked you asks for a fix.

```text
---
_Generated by [Claude Code](https://claude.ai/code)_
```
